# Preliminary independent Codex case comparison

Date: 2026-10-05. Three independent subagents ran v0.1, then three fresh independent subagents ran v0.2. Each read only its own packet and verified sources. No ChatGPT UI conversation was created. No real banking application or MCP implementation was tested. These are model-response tests of specialist instructions.

## Observed stability
All six outputs identify MCP's November 2024 launch, JSON-RPC/client-server predecessors, and the distinction between MCP, server implementations, APIs, REST and HTTP. All keep durability conditional and treat MCP as able to coexist with APIs. Sources and wording differ between independent generations; historical stability is semantic, not byte-for-byte identity. Model-capability evidence also varies: primary outputs cite original research, while retail v0.2 explicitly marks that enabling capability as unverified.

## Observed contextual change
- Read-only banking: authoritative customer/promotion lookup, privacy, freshness, and explanation fidelity; no enrollment or record changes.
- Same bank with writes: authoritative enrollment and updates add duplicate submission, partial completion, stale approval and recovery concerns. Human approval is not treated as verified protection. These are specialist handoff questions, not a production control approval.
- Small retailer: catalog/inventory/public promotion freshness and limited maintenance capacity; direct integration may be preferable where actual cross-host demand is absent. It excludes customer financial records and transactional writes.

These observations compare saved actual outputs, not projected outcomes. General history is not rewritten by the organization's risk tolerance.

## Preserved failure and unchanged-case retest
Retail v0.1 includes irrelevant bank-specific evidence requests in limitations and abstention fields. The instructions had embedded bank-specific requirements without gating them by the active case. The retail additional_context also includes residual banking wording. That input remains unchanged, including the inconsistency, so the retest does not remove the failure trigger.

Revision v0.2 makes explicit intake fields govern the active organization/application, limits banking requirements to banking cases, and requires acknowledgment of mismatched residual context without importing irrelevant requests. Retail v0.2 limitations and information requests cover catalog permissions, freshness, promotion applicability/expiry, intended hosts and maintenance ownership; bank-specific requests no longer appear. This is one observed improvement, not proof of robustness across arbitrary prompts. Readability and evidence-discipline instructions were also strengthened, so the retest does not isolate a single causal variable.

## Validation and residual limitations
All six outputs pass the included basic validator and a separate check against the frozen schema's required fields, nested types and prohibition of extra top-level fields. All three case checksums are unchanged. Frozen-core integrity passes. Structural validity is distinct from factual and analytical quality.

No measurements establish actual interoperability, cost reduction, reliable banking execution, or the causal drivers of REST adoption over twenty years. MCP's version-specific documentation is evidence of specified behavior, not tested host support. Scientific predecessor evidence is uneven across runs. The durability finding remains a conditional architectural inference. Two runs per case do not estimate reliability or forecast accuracy.

## Suggested student assessment
The tested specialist provides a usable starting creation analysis and separates historical facts from contextual implications. The observed context error improved after revision, but the student must inspect sources and outputs, supply an independent judgment, and perform the course-required ChatGPT runs before presenting this as a completed assignment.
